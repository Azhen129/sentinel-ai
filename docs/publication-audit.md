# Public repository preparation audit

**Audited: 30 October 2026.** Scope: the existing Sentinel AI project, its owned source/configuration, documentation, screenshots, fixtures, included model, dependency manifests and existing tests. The application was not rebuilt, retrained or redesigned.

This report records the initial publication-preparation stage and its original file/test scope. A subsequent, separately implemented bounded Windows monitor extension is summarized in [the update below](#subsequent-monitor-profile-extension); the current [manifest](publication-files.txt) includes its public source files. The original audit verdict/check counts are historical rather than a claim that new hardware capture was verified.

## Verdict

**The reviewed source and approved artifacts are suitable for publication as an educational, synthetic-demo project, using the updated ignore rules and reviewed file manifest. The entire working directory must not be uploaded wholesale.** Local environments, dependencies, caches and runtime databases are still present for development and intentionally excluded. No secret was detected in the reviewed publication candidates; this is a scoped review, not a guarantee about future files or force-added ignored material.

The application does **not** provide proven live network protection. Its default dashboard replays synthetic traffic. Optional lab mode reads already collected files; it does not implement an active sensor, scanning, blocking or automatic response. The benchmark model has low recall and is not a validated production intrusion detector.

No Git repository/history was present in this folder at audit time. Consequently there was no existing commit history or staged index to inspect for previously committed secrets. This stage did not initialize the project's Git repository, create commits, push, deploy, or modify the existing portfolio. Git-ignore behavior was checked with an isolated audit harness outside the project.

## Sensitive-data and artifact review

- A redacted pattern scan of owned text/config files checked credential-shaped tokens, private-key headers, credential-bearing URLs, assignment candidates and machine-specific user paths. No real credential or personal absolute path was detected. The only initial assignment candidate was a test-only key in `tests/test_backend.py`.
- Dependency/virtual-environment contents and caches were not treated as publication source or scanned as if they were owned application code. They remain excluded. The scan did not print secrets or dump incident notes.
- The current local database held 360 demo-origin connections and 56 incidents. Its 720 source/destination address occurrences were documentation-range addresses. It remains excluded regardless: a later run or an investigation note could contain private information. No SQL data writes or deletions were issued, and the main database/WAL payload checksums were preserved. Read-only SQLite inspection updated reader-coordination bytes in the excluded `.db-shm` sidecar; that runtime coordination file was not restored while the database could be in use.
- The three synthetic traffic fixtures contain 22 records and 44 address occurrences, all in RFC 5737 documentation ranges. The five existing screenshots were visually reviewed; they show the synthetic application/public benchmark information and no identified private credentials or machine paths. No screenshots were fabricated or recaptured.
- The 317,115-byte model matches its trusted build and `metrics.json`: SHA-256 `856206a435150c9075366fd93617c2eadbe9973eb233c1cd3622f7d514bb6222`. Review found the expected scikit-learn preprocessing/Isolation Forest state and public aggregate/category information, with no detected credential, private identifier, user-specific path or raw-row payload. The model and evaluation bytes were preserved.
- Dataset attribution and provenance are retained. The [official UCI catalog](https://archive.ics.uci.edu/dataset/130/kdd+cup+1999+data) lists CC BY 4.0; the model card/data documentation include the authors, DOI, source/mirror and checksums. The raw benchmark download is not required for runtime publication.
- Joblib is pickle-based and must be loaded only from trusted sources. A matching hash detects accidental mismatch; it is not a digital signature or protection against replacement of both model and metadata. See [SECURITY.md](../SECURITY.md).

## Changes made in this stage

1. Expanded Git exclusions for environment variants, credential/key files, databases and sidecars, compressed captures, common Zeek JSON logs, downloads, exports, caches and temporary files. Data/model directories now allow only the reviewed files by default.
2. Hardened both Docker-context ignore files so ignored environment secrets, SQLite sidecars and traffic files are not inadvertently sent in build contexts. The backend context excludes the entire runtime `data/` directory; the backend image already creates its own empty data directory.
3. Reworked the README around actual features, architecture, install commands, limitations, screenshots, measured model results and explicit synthetic-demo/no-proven-protection wording. Fixed Ubuntu's interpreter choice, consistently qualified venv commands, documented Node 22.12+, and explained that backend `.env` loading is explicit while frontend `VITE_` configuration is public.
4. Added a blank frontend environment example, `.gitattributes` for text/binary handling, this audit, the reviewed file manifest and `SECURITY.md`. Updated supporting training-documentation links.
5. Added a CI check requiring the included model/metadata to load successfully, so a missing artifact cannot be hidden by a skipped positive test. CI installs current packaging tools first. Corrected an older verification statement: the workflow selects Python 3.11, not an executed Python 3.12 matrix.

Backend behavior, frontend application code, SQLite contents, model/evaluation artifacts, detection rules, replay logic, existing tests, requirements and frontend dependency versions/lockfile were preserved. No package upgrade or clean reinstall was performed in the existing environment.

## Remaining work and limitations

- **Before any future commit:** compare the staged names/diff with the manifest, keep all runtime/secret material excluded, and re-scan any new files. Ignore rules cannot identify arbitrary private JSON placed under an unrelated filename, and `git add -f` can override them. If existing history is introduced later, audit that history separately.
- **Validation still pending:** Docker image build/Compose startup, container-image advisory scan, remote Linux CI, fresh Linux/Python 3.12 installation and real Zeek/tshark execution. Docker's engine was unavailable here. This audit did not rebuild the frontend or reinstall dependencies; the previous production-build/browser evidence remains separately dated in [verification.md](verification.md).
- **Minor cleanup:** the training CLI's missing-file error mentions `.gz/.csv`, although checksum validation accepts the original compressed archive. README instructions correctly require that archive. The model-card generator still emits a generic `python` command; a future documentation-only edit can synchronize it with the README. Neither issue prevents the documented demo from running.
- **Presentation:** several JPEG screenshots are visibly compressed. Optional lossless recapture would improve a future portfolio showcase, but current images are real, reviewed evidence.
- **Service limits:** one worker and shared state, no multi-user authentication for reading/editing incidents, keyed ingestion only, and limited five-tuple PCAP aggregation. Publishing source does not approve exposing lab data or operating an Internet-facing SOC service.
- **Model limits:** held-out precision 51.04%, recall 20.12%, F1 28.86% and benign false-positive rate 3.16% on an old lab benchmark. It missed 2,235 of 2,798 test attacks. This is an educational baseline, not proven live network protection.

No application-level blocker was found for publication of the reviewed source and approved artifacts with those boundaries. Publication, deployment and portfolio integration remain separate, unperformed stages.

At this monitoring-extension stage it grew to 77 with eight public source/guide/test files: `backend/app/monitoring.py`, `detection/collector.py`, `scripts/monitor_windows.py`, `tests/test_collector.py`, `tests/test_monitoring.py`, `frontend/src/presentation.ts`, `frontend/tests/presentation.test.mjs`, and `docs/windows-monitoring.md`. The extension implements an explicitly authorized, bounded local collector, so the initial statement about the file-import lab having no active sensor remains limited to that profile. The API/browser never starts capture. dumpcap stdout feeds TShark stdin without requesting a raw packet file; 128-byte prefixes can still contain application fragments in RAM. Only allowlisted metadata is exported. Interface IDs, assigned addresses, keys, monitor databases, exports, actual local screenshots, and private run evidence are excluded from public documentation and the manifest.

The implementation-stage checks and their exact scope are in [verification.md](verification.md#optional-windows-monitoring-update): 116 Python tests, four frontend tests, TypeScript/UI build, a synthetic in-memory decode using actual TShark, and an empty isolated-monitor HTTP smoke check. No continuous or proven live protection is claimed. The original 53-test/audit/browser rows above remain the earlier baseline. New-policy GUI validation, Docker startup, remote CI and fresh-platform installation limits are separate; no push, public deployment or portfolio change is implied.

## Final v1 preparation — 7 November 2026

This dated section records the subsequent release work. Earlier counts, packaging-tool findings and browser restrictions above describe their original inspection dates; they are not the current validation result. The existing application, historical model and private evidence remain the basis of this release. No project rebuild, Git initialization, push or public deployment was performed.

### Implemented release boundaries

- The new explicit public-demo profile creates or reopens only its dedicated `public_demo` database role, seeds a frozen **360-record synthetic snapshot**, and refuses monitoring, lab and PCAP flags. Existing private, unmarked and incompatible databases are refused before normal writable storage opens. Every unsafe API method is rejected with HTTP 403, including replay, reset, imports and incident edits. The frontend also presents read-only controls. Ordinary local Demo Mode retains its editable workflow.
- The separate public-demo Compose file uses its own named volume, publishes only the frontend on `127.0.0.1:8082`, and publishes no backend host port. Runtime data, packet captures, keys and private configuration remain outside Docker contexts and the reviewed publication manifest. This local configuration is preparation evidence, not a public deployment.
- Private monitor and lab APIs now enforce loopback socket peers, one allowed loopback Host header and trusted browser origins for writes. Ingestion/profile key checks remain separate. **Private browser reads and incident edits use local-machine trust, not a login or per-user key.** Other local users/processes are within that trust boundary; these profiles must not be exposed through a public proxy. CORS alone is not authorization.
- The lab-import client refuses nonliteral-loopback destinations, proxies and redirects; input, acknowledgments and blocking operations are bounded. Errors do not print submitted keys or response bodies. The launcher passes secrets only through its owned backend's process environment or a private prompt for an explicitly reused service; no capture key is sent to the browser or stored in its adapter preference.
- The Windows launcher is disabled by default and requires a fresh wired-adapter selection plus `START` for one bounded 15-second collection. It rejects stale/incompatible backend contracts, stops on disconnect rather than choosing another adapter, and stops only processes that it created. It does not elevate, install drivers, change security settings or offer a browser capture-command endpoint. Its frontend environment review permits only comments/blanks and the two documented literal monitor settings, rejecting other assignments, expansion and multiline syntax. The collector implementation and actual opt-in flags are retained.
- UI changes prevent an unavailable backend from being mislabeled as Demo, hide stale filtered results/exports, bound requests, improve drawer error/cancellation handling and keyboard navigation, preserve CSV provenance, and distinguish controlled endpoint evidence from packet-decoder observations. Informational live model scores remain distinct from security findings.

### Publication decision and final gates

The [reviewed publication manifest](publication-files.txt) defines the intended source, tests, synthetic fixtures, approved model files, notices, documentation and genuine nonprivate screenshots. It does not authorize adding the complete working directory. Monitoring/demo/lab databases and sidecars, captures, metadata exports, launcher preferences, credentials, local environment files, test/audit evidence, caches and build output remain private/excluded. The final manifest and scoped sensitive-pattern check must match the exact files eventually committed; ignore rules do not sanitize arbitrary text or Git history.

**Final preservation check passed:** stable byte copies of the original main databases and WAL files matched the before snapshots in every table-content fingerprint and passed SQLite integrity checks. Monitoring retains 18 live records, two historical incidents and all three history entries, including the original note. Demo retains 360 records, 56 incidents and 57 history entries; metadata and monitor batch tables also match. Original model files, feature/inference/training code, rule engines, dependency pins/lockfile, MIT license and the five older screenshots retain their hashes. Test and browser writes targeted disposable copies.

With preservation verified and subject to the final exact manifest check, the reviewed source is eligible for public-repository preparation with its documented limits. Public deployment remains a separate decision: use the isolated read-only synthetic profile, validate the chosen frontend/backend/storage architecture, then complete container/hosting checks and obtain the owner's explicit deployment approval. No live-capture service or private database belongs in that deployment. The existing localhost application and a source release do not provide proven live network protection or whole-home visibility. Whole-home monitoring would require separately authorized gateway/export support or a mirror/TAP and appropriate sensor, not a dashboard setting. No router, firewall, Npcap or Windows permission change was made.
